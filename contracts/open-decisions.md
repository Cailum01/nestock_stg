# 待決定事項

這份檔案列出還沒定案、而且會影響多位負責人的事。
**AI 和組員在實作相關功能之前，必須先讀這份檔案。**

- **已定案**：照決定做。
- **待決定、有提案**：照提案做，做法要容易修改，並在 PR 說明寫「依 D-x 提案暫定」。
- **待決定、沒有提案**：停下來，告訴使用者這件事還在等決定。

**怎麼定案**：每一項都有截止日。截止日前在群組或 PR 提出反對，就另外討論；
**截止日前沒人反對，就照提案定案**。定案後由提案人開 PR，把狀態改成「已定案」，

## D-1 確認卡的有效期限

- **狀態**：待決定（有提案）；截止日 2026-11-05
- **要誰決定**：全組
- **意思**：確認卡跳出來之後，保留多久讓使用者決定。這段時間內，使用者隨時可以按確認或取消。
- **提案**
  1. 超過時間後，確認卡失效。這時候按確認，一律拒絕、不寫入，並請使用者重新問一次。
  2. 使用者下次傳訊息給 Agent 時，Agent 會順便提醒還沒處理的確認卡。這不需要背景排程或推播，
     符合 v8 的範圍。
- **待決定**：時間要多長。請考慮兩種情況：
  1. 使用者被打斷，晚一點才回來按。時間太短的話，使用者常常要重新問。
  2. 家裡的庫存在這段時間內被別人改了。時間太長的話，確認卡上的數字可能已經過時。

  另外，Demo 現場講解的時間也不能超過這個期限。
- **暫時做法**：時間長短還沒定案之前，期限要做成可以調整的設定，不要把數字寫死在程式裡。

## D-2 暫停中的確認卡存在哪裡

- **狀態**：待決定（有提案）；截止日 2026-11-05
- **要誰決定**：B1 任軒主答，A1 Jason 一起確認
- **背景**：目前暫停狀態存在伺服器的記憶體裡。伺服器重開後，還沒按的確認卡會全部失效。
- **提案**：每張確認卡在 Cosmos 存一筆「確認紀錄」，放在該家庭的分區。
  - 用 Cosmos 的 TTL，讓紀錄在 D-1 決定的時間後自動刪除。
  - 用 etag 確保狀態只能從「等待中」改一次，防止同時按兩次。
- **待決定**：放在哪個 container（container 設計歸 B1）。
- **相關**：TTL 的時間取決於 D-1；能不能和其他寫入放進同一個批次，取決於 D-3。

## D-3 一張確認卡上有好幾件東西

- **狀態**：待決定（有提案）；截止日 2026-11-05
- **要誰決定**：B1 任軒、C1 Judy、C2 兔毛；A2 宗逸請一起看（Issue #6 曾問過 A1 這題）
- **提案**
  - a. 一張確認卡對應一個 `approval_id`，裡面每一件東西各有自己的 `operation_id`。
  - b. 同一張卡的寫入一起成功或一起失敗，使用同一家庭分區的 Cosmos 批次交易。
    C1 的完成購買也照這個規則。
  - c. 使用者只勾其中幾件時，App 在確認時多傳「勾了哪幾件」。只能從卡片上顯示的項目裡挑，
    沒勾的不寫入。`ResumeRequest` 需要加欄位。欄位格式見 D-10 第 5 點
    （回傳格式由 A1 和 C2 決定，照 v8 第 12 節）。
  - d. 使用者在確認卡或 Vision Review 改了數值時，App 把修改送回 Agent，由 Agent 重新產生一張
    新的確認卡，使用者再確認一次。**不可以**把修改後的數值直接送到 `/agent/resume`。
- **待決定**：b 在 Cosmos 上是否可行；c 和 d 的欄位格式。

## D-10 比價確認卡的格式

- **狀態**：已定案（照 v8 第 12 節「Purchase Options — Workflow D」，2026-11-03）
- **要誰照做**：A1 Jason（確認卡與 resume 檢查）、A2 宗逸（比價選項）、C2 兔毛（卡片畫面）、
  C1 Judy（加進待購清單）
- **決定**
  1. 一張比價卡只比一樣東西，整張卡一個 `operation_id`；每個選項有自己的 `option_id`。
  2. 每個選項的欄位：店家（`store`）、商品、價格、網址、更新時間，以及 `source`
     （`live` 或 `demo`）。示範資料不可以假裝成即時資料。價格只顯示，不存。
  3. 卡片本身就是確認畫面。使用者選一個選項並確認一次，不再跳第二個確認視窗。
  4. 選了選項就回傳 `selected_option_id`（必填）。按取消就是 `approved=false`，
     什麼都不寫，也不看 `selected_option_id`。
  5. 三種確認卡共用同一個回傳格式：`approval_id`、`approved`、
     `approved_operation_ids`（只有勾選好幾件的卡用，見 D-3）、`selected_option_id`
     （只有比價卡用）。
  6. 確認後沿用卡片的 `operation_id` 加進待購清單；重試時不會重複加。
  7. MVP 只接一個比價來源，來源可以替換；不做全網爬蟲或多電商爬蟲（v8 第 1、6 節）。
- **後續**：`ResumeRequest` 目前只有 `approved`，要新增 `approved_operation_ids` 和
  `selected_option_id`。由 A1 修改 `backend/app/models/agent.py`，並和 C2 對齊。
